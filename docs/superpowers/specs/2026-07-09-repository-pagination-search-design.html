Design Spec

Repository Pagination and Search

Date: 2026-07-09

Scope: Backend API, store query contract, OpenAPI schema, and the authenticated Repositories page in apps/web.

Summary

Introduce repository search and pagination as a backend collection contract, not as client-side filtering over a full result set. The Repositories page should become URL-driven through q, page, and page_size query parameters. The API should return a typed envelope with result items and pagination metadata.

Recommended solution: evolve GET /api/v1/repositories into a searchable, paginated endpoint backed by SQL filtering, stable ordering, and a total count.

The default UI page size should be 25 repositories. This keeps the table compact enough for the current product layout, gives users meaningful scan density per page, and avoids making the first authenticated render depend on a large tenant-wide result set.

Goals

  • Allow users to find repositories by name or URL from the Repositories page.
  • Prevent large tenants from loading every repository just to render the first screen.
  • Make pagination state shareable and refresh-safe through URL parameters.
  • Create an API response shape that can grow with metadata without breaking consumers again.
  • Keep repository ordering deterministic across page transitions.

Non-Goals

  • Do not add repository creation, deletion, or edit workflows.
  • Do not introduce client-side data libraries for this page unless later interactivity requires them.
  • Do not add cursor pagination in the first implementation.
  • Do not redesign the app shell or table visual language.

Current State

The Repositories page calls listRepositoriesServer(), which fetches GET /api/v1/repositories. The endpoint currently returns a raw JSON array of RepositoryListItem. The store query returns all repositories for the tenant ordered by r.name asc, r.id asc.

The Scans page also depends on the same full repository list for its repository selector and default redirect. This makes the endpoint shape a shared contract, so all consumers need to be updated in the same change.

API Contract

Endpoint

GET /api/v1/repositories?q=&page=1&page_size=25

Query Parameters

Name Type Default Validation Behavior
q string empty Trim whitespace. Maximum 200 characters. Case-insensitive search across repository name and URL.
page integer 1 Must be greater than or equal to 1. One-based page number.
page_size integer 25 Allowed range: 1 to 100. Maximum number of items returned in one response. The Repositories UI uses 25 by default.

Response

{
  "items": [
    {
      "id": "11111111-1111-1111-1111-111111111111",
      "name": "deplens-platform",
      "url": "https://github.com/ferretsecurity/deplens-platform",
      "default_branch": "main"
    }
  ],
  "pagination": {
    "page": 1,
    "page_size": 25,
    "total": 73,
    "total_pages": 3,
    "has_previous": false,
    "has_next": true
  },
  "filters": {
    "q": "platform"
  }
}

Errors

  • Invalid page, page_size, or oversized q returns 400 Bad Request.
  • Unauthenticated or unauthorized requests keep the existing 401 Unauthorized behavior.
  • A page beyond total_pages returns an empty items array with accurate pagination metadata, not an error.

Search Semantics

  • Search is case-insensitive.
  • Search matches repository name and url.
  • The initial implementation should use escaped ILIKE patterns to avoid wildcard abuse through user input.
  • Empty or whitespace-only q is equivalent to no search filter.
  • Default branch search is intentionally excluded at first because users primarily identify repositories by name or origin URL.

SQL Safety

SQL injection protection should come from parameterized queries through pgx, the same database driver pattern already used in the store layer. The implementation must never concatenate q, page, page_size, limit, offset, or sort fragments into SQL strings.

This is enough for SQL injection as long as every user-controlled value is passed as a bind parameter such as $1, $2, and $3. Search needs one additional guard that is not SQL injection protection: escaping %, _, and \ before building the ILIKE pattern, so user input cannot accidentally become an unbounded wildcard query. 

func escapeLikePattern(value string) string {
    value = strings.ReplaceAll(value, `\`, `\\`)
    value = strings.ReplaceAll(value, `%`, `\%`)
    value = strings.ReplaceAll(value, `_`, `\_`)
    return value
}

pattern := "%" + escapeLikePattern(query) + "%"

where r.tenant_id = $1
  and (
    $2 = ''
    or r.name ilike $3 escape '\'
    or r.url ilike $3 escape '\'
  )

page and page_size should be parsed as integers, range-checked, converted into limit and offset, and then passed as bind parameters. The implementation should not support client-provided sort fields in this change, which avoids dynamic ORDER BY SQL entirely.

Sorting and Pagination Semantics

Results should use a stable default order of lower(r.name) asc, r.id asc. The id tiebreaker prevents rows with equivalent names from moving between pages.

Offset pagination is the right first implementation because the product needs numbered pages, total counts, and straightforward URL state. Cursor pagination can be added later if tenant repository counts become large enough that offset scans are a real bottleneck.

Backend Design

Store Types

type RepositoryListFilter struct {
    TenantID  string
    Query     string
    Page      int
    PageSize  int
}

type RepositoryListPage struct {
    Items      []RepositoryListItem `json:"items"`
    Pagination PaginationMetadata   `json:"pagination"`
    Filters    RepositoryFilters    `json:"filters"`
}

type PaginationMetadata struct {
    Page        int  `json:"page"`
    PageSize    int  `json:"page_size"`
    Total       int  `json:"total"`
    TotalPages  int  `json:"total_pages"`
    HasPrevious bool `json:"has_previous"`
    HasNext     bool `json:"has_next"`
}

type RepositoryFilters struct {
    Query string `json:"q"`
}

Store Method

ListRepositories(ctx context.Context, filter RepositoryListFilter) (RepositoryListPage, error)

SQL Shape

with filtered as (
  select r.id, r.name, r.url, r.default_branch
  from repositories r
  where r.tenant_id = $1
	    and (
	      $2 = ''
	      or r.name ilike $3 escape '\'
	      or r.url ilike $3 escape '\'
	    )
	),
counted as (
  select count(*) as total
  from filtered
)
select f.id, f.name, f.url, f.default_branch, c.total
from filtered f
cross join counted c
order by lower(f.name) asc, f.id asc
limit $4 offset $5;

The implementation may use two queries instead of the CTE if that is clearer. The important contract is that total counts the filtered result set and that rows use the same filtered scope.

HTTP Handler

  • Authorize the request exactly as the current ListRepositories handler does.
  • Parse and validate q, page, and page_size before calling the store.
  • Normalize q by trimming whitespace.
  • Return the envelope directly from the query service.
  • Keep tenant scoping inside the store filter, not in web-layer code.

Web UI

The Repositories page remains a server component. It reads searchParams, calls listRepositoriesServer with normalized parameters, and renders the current result page.

URL State

/app/repositories?q=platform&page=2&page_size=25

Page Structure

  • Header: title and concise description.
  • Search form: single input named q, submit button, hidden page_size, and no hidden page so searches reset to page 1.
  • Results summary: show Showing 26-50 of 73 repositories when results exist.
  • Table: same columns as today, populated from items.
  • Pagination controls: previous and next links, plus nearby page links where useful.
  • Empty state: distinguish between no repositories uploaded and no repositories matching the current search.

Search Behavior

  • The form submits with method get.
  • Submitting a new search resets page to 1.
  • A clear action links to /app/repositories when q is active.
  • Pagination links preserve q and page_size.

Frontend Compatibility

All current frontend callers of listRepositoriesServer() must be updated as part of this work. The breaking API response shape is acceptable only if the frontend migration happens in the same implementation.

Required Frontend Changes

File Current Assumption Required Change
apps/web/src/lib/types.ts Only RepositoryListItem exists. Add RepositoryListResponse, PaginationMetadata, and RepositoryListFilters.
apps/web/src/lib/queries.ts listRepositoriesServer() returns RepositoryListItem[]. Return RepositoryListResponse and accept optional q, page, and page_size params.
apps/web/src/app/app/repositories/page.tsx Maps directly over the returned array. Read searchParams, render response.items, and use response.pagination for result count and page links.
apps/web/src/app/app/scans/page.tsx Uses the full array for the repository selector and default repository. Use a selector-specific helper so the page still receives RepositoryListItem[] until a searchable combobox is added.
apps/web/src/app/app/repositories/[repositoryId]/manifests/page.tsx Uses the full array to find the active repository display name. Use the selector helper temporarily, or prefer a future GET /api/v1/repositories/{id} detail endpoint.
apps/web/src/app/app/repositories/page.test.tsx Mocks listRepositoriesServer() as an array. Mock the response envelope and add assertions for search and pagination UI.
apps/web/src/app/app/scans/page.test.tsx and manifest page tests Expect repository helper data in array form. Update mocks to use the selector helper or the new envelope, depending on each page's final dependency.

Compatibility Helper

The Scans page currently expects listRepositoriesServer() to return an array. The implementation should update that helper to expose the new envelope and add a temporary helper for selector use: 

listRepositoriesServer(params): Promise<RepositoryListResponse>
listRepositoryOptionsServer(): Promise<RepositoryListItem[]>

listRepositoryOptionsServer() can call GET /api/v1/repositories?page=1&page_size=100 for now and return only response.items. This keeps existing selector pages working while making the repository list contract long-term ready. If tenants regularly exceed that selector size, the Scans page and manifest detail page should stop loading repository options and use repository-specific lookup endpoints or a searchable repository combobox backed by the paginated endpoint.

OpenAPI

  • Add q, page, and page_size query parameters to /api/v1/repositories.
  • Add RepositoryListResponse, PaginationMetadata, and RepositoryListFilters schemas.
  • Change the 200 response schema from an array to RepositoryListResponse.
  • Update spec tests that currently assert the raw array response.

Compatibility

This change breaks consumers that expect GET /api/v1/repositories to return a raw array. Because this API is still compact and internally consumed by the web app, the cleaner long-term move is to update the endpoint in place and update all in-repo callers.

If external API compatibility is required before implementation, add a new endpoint such as GET /api/v1/repositories/search for the envelope and keep the existing array endpoint temporarily. That should be treated as a compatibility bridge, not the preferred final design.

Performance

  • The baseline implementation is acceptable with the existing tenant-scoped repository table and page size cap.
  • If search latency becomes visible, add a Postgres trigram index for name and url.
  • Keep page_size capped at 100 to protect response size and count query cost.
  • Do not cache authenticated repository responses globally because they are tenant-scoped.

Testing

Store Tests

  • Returns the first page with the expected total and total_pages.
  • Filters repositories by case-insensitive name match.
  • Filters repositories by case-insensitive URL match.
  • Does not leak repositories from another tenant into results or counts.
  • Uses deterministic ordering when names collide.

HTTP Tests

  • Parses valid pagination and search query parameters.
  • Rejects invalid page, page_size, and oversized q.
  • Returns the new response envelope.
  • Preserves authorization behavior.

Frontend Tests

  • Renders repository rows from items.
  • Renders the search input with the active query.
  • Builds previous and next links that preserve search parameters.
  • Shows the no-upload empty state when total is 0 and q is empty.
  • Shows the no-match empty state when total is 0 and q is present.

OpenAPI Tests

  • Asserts the repository list response references RepositoryListResponse.
  • Asserts query parameters include q, page, and page_size.

Implementation Order

  1. Add store filter, pagination metadata types, and paginated repository query.
  2. Update the HTTP query interface, handler parsing, validation, and tests.
  3. Update OpenAPI schemas and spec tests.
  4. Update apps/web/src/lib/types.ts and apps/web/src/lib/queries.ts.
  5. Update the Repositories page to render search, result count, empty states, and pagination links.
  6. Update the Scans page and repository manifest page consumers through a compatibility helper or endpoint-specific lookup follow-up.
  7. Run Go, API spec, and web tests.

Acceptance Criteria

  • /app/repositories loads the first page of repositories without fetching the entire tenant repository set.
  • /app/repositories?q=repo shows only matching repositories and keeps the query visible in the search input.
  • Pagination controls preserve active search state.
  • The API returns items, pagination, and filters for repository lists.
  • Invalid pagination input returns 400 Bad Request.
  • The Scans page still renders after the repository API response shape changes.
  • The repository manifest page still renders after the repository API response shape changes.
  • Store, HTTP, OpenAPI, and frontend tests cover the new contract.
